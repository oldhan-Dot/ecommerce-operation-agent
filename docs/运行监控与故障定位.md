# 运行监控与故障定位

管理员进入“运行监控”。接口为 `GET /api/v1/operations/summary`，每10秒刷新，页面隐藏时暂停，回到页面立即刷新。所有模型/导入/运维事件只聚合当前企业。

最近5分钟展示模型完成数、失败数/率、超时、输出校验失败、已返回Token和时延P95；未返回用量不推算费用。队列展示等待数、最长等待、运行调用。HTTP P95及5xx数是当前API进程最多10000条的有界窗口，生产多副本需汇总JSON日志。导入总耗时包含上传、人工确认等待及处理，并非纯执行耗时。

Worker独立线程每10秒在独立短事务写心跳，不受模型HTTP等待阻塞；超过30秒或没有记录时页面提示未就绪。心跳正常只证明Worker进程和数据库连接活跃，任务成功仍以任务状态为准。外部探测器应同时检查API就绪接口和Worker心跳，避免API停机后无法在页面发现异常。

模型已完成样本≥10且失败率≥20%、排队≥9分钟时，监测线程产生 `OPS_MODEL_FAILURE_RATE`、`OPS_QUEUE_WAIT` 审计及JSON事件。同一企业同类事件5分钟节流，多Worker通过企业锁防止重复。数据库不可用、导入清理失败输出脱敏JSON事件；数据库故障期间不能保证审计落库。外部通知接收器、备份失败告警和日志保留由部署环境配置，本机没有接入邮件或即时消息。

API日志只包含路由模板、请求编号、方法、状态和耗时，不含查询参数、Cookie、密码或正文。模型调用完成日志含call_id/task_id/状态/耗时/错误码。审计页面可按请求编号、对象类型/编号、动作精确查询；任务完成审计使用 `ai-task-{id}`，导入Worker用租约关联编号，审核/导出含指定版本编号。不要把完整HTTP请求、提示词或原始供应商异常写入采集系统。

排查顺序：

1. 查看 `/api/v1/health/ready` 返回数据库连接或迁移错误；迁移由运维命令显式执行。
2. 检查Worker心跳、队列最长等待和Worker日志；只有API启动时，任务不会被执行。
3. 通过task_id定位调用、快照与完成审计，通过request_id定位写操作。授权撤销、配置变更或围栏变化会导致任务被拒绝/丢弃，不要手动把失败改为成功。
4. 不确定调用不自动重放；确认后在页面显式重试。每日额度不会因超时/失败返还，避免重复计费。
